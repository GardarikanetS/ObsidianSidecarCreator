# 1 Концепция и Назначение
Плагин предназначен для решения проблемы отсутствия поддержки метаданных (YAML/Properties) и полноценного управления для non-markdown файлов (PDF, изображений, видео, офисных документов).
Решение: Автоматическое или ручное создание файла-компаньона (Sidecar) в формате .md, жестко связанного с оригиналом.

Ключевые цели:
1. Обеспечить возможность добавления метаданных и тегов к любому типу файлов.
2. Реализовать бесшовную навигацию между оригиналом и его описанием.
3. Улучшить UX работы с вложениями прямо в тексте заметок (интерактивные кнопки).

# 2 Структура и Хранение Файлов
2.1 Именование (Naming Strategy)
Пользователь имеет полный контроль над шаблоном имени sidecar-файла.
- Настройка паттерна: Текстовое поле с поддержкой переменных.
- Значение по умолчанию: `{{originalName}}.{{originalExt}}.md`
- Доступные переменные:
    - `{{originalName}}` — имя файла без расширения.
    - `{{originalExt}}` — расширение оригинального файла.
    - `{{date}}` — текущая дата.

2.2 Локация хранения (Storage Location)
Выбор места создания sidecar-файла через Dropdown-меню в настройках:
1. Same Folder (Default): В той же папке, где лежит оригинальный файл (Colocation).
2. Vault Root: В корневом каталоге хранилища.
3. Custom Folder: В папке, путь к которой задан пользователем вручную.
4. Active File Folder: В папке, где находится *активный* (открытый в данный момент) файл, из которого происходит создание.

2.3 Содержимое Sidecar (Content & Templates)
Выбор движка шаблонизации в настройках:
1. Default Template: Простой встроенный шаблон.

Структура по умолчанию (Default Template):
```markdown
---
tags:
  - sidecar
sidecar_linkToOriginal: [[originalName.originalExt]]
sidecar_hash : hash
---

![[originalName.originalExt]]

# About
```
- Поле `linkToOriginal`: Содержит Wiki-ссылку на оригинальный файл. Критически важно для работы функций Relink и навигации.
- Тег `#sidecar`: Обязательный системный маркер.
- Секция `# About`: Информация о файле в свободном виде, которую пользователь вносит вручную

2. Templater: Использование внешнего файла-шаблона (интеграция с плагином Templater). Пользователь указывает путь к `.md` файлу шаблона.

2.4 Порядок применения шаблонов (Template Pipeline):

1. Создается sidecar-файл по выбранному движку:

- Built‑in: используется встроенный шаблон.

- Templater: берется указанный .md файл-шаблон.

2. Затем выполняется подстановка переменных Sidecar (например {{originalName}}, {{originalExt}}, {{date}}, а также вычисленных полей вроде hash).

3. Затем (если включено и плагин Templater установлен) выполняется обработка Templater (его синтаксис/код). Выполнение шаблонов может исполнять пользовательский код, поэтому считается потенциально небезопасным и должно быть явно включаемым поведением.

# 3 Логика Синхронизации и Файловых Операций (Backend)
3.1 Создание Sidecar-файла
существует 2 способа добавления файла в vault:
1. obs открыт, перехватывет новый файл, можно подписаться на событие
	1. добавление просто в хранилище — создается новый sidecar файл и больше ничего не происходит
	2. добавление происходит в активный файл (действия происходят строго в такой последовательности)
		1. создается новый sidecar файл
		2. если чекбокс "disable auto embed" в настройках активен, ссылка в активном файле с `![[original.ext]]` меняется на `[[original.ext]]
		3. если чекбокс "Auto swap link in active file" в настройках активен, ссылка в активном файле с `[[original.ext]]` меняется на `[[original.ext.md]]
2. obs закрыт и не знает о добавлении нового файла
	1. ручное сканирование всего волта на наличие original файлов без Sidecar
		- можно запустить командой "Scan vault"
		- можно в настройках нажать кнопку "Scan vault"
	2. автоматическое сканирование всего волта при запуске Obsidian
		- cканирование происходит в фоне, после иницализации, в процессе вешается уведомление "Sidecar: идет сканирование хранилища"
		- нужно какое то кеширование, чтобы процесс шел эффективно, особенно в мобильной версии
При этом, эти методы добавления должны быть логически несвязаны, разнесены в коде, у них должны быть разные черные/белые списки и настройки
3.2 Разрешение конфликтов имен
Настройка с 3 вариантами поведения при попытке создать файл, который уже существует:
	3. Sync (Синхронизация): Добавить недостающие метаданные (теги, linkToOriginal) в YAML существующего файла, не трогая контент.
	4. Increment (Дублирование):
		- Переименовать *оригинал* в `name 1.ext`.
		- Создать новый sidecar `name 1.ext.md`.
	5. Manual (Вручную): Показать модальное окно с выбором действия.

3.2 Переименование и Перемещение (Sync Logic)
Плагин подписывается на API события `vault.on('rename')`.
1. Двусторонняя связь:
    - При переименовании/перемещении *Оригинала* -> автоматически переименовывается/перемещается Sidecar.
    - При переименовании/перемещении *Sidecar* -> автоматически переименовывается/перемещается Оригинал.
2. Обработка внешних изменений (External Rename):
    - Если файл переименован вне Obsidian, связь теряется.
    - Решение: команда "Relink Sidecar". Пользователь вручную указывает новый файл для "осиротевшего" sidecar. Плагин обновляет поле `linkToOriginal` и имя файла.
3. Advanced Rename Detection (Хеширование):
    - Опциональная настройка. Плагин хранит хеши оригиналов. При запуске пытается найти потерянные файлы по хешу и предложить автоматическое восстановление связи.
	- реализуем стратегию "Head-Tail Hash"
		1. читаем первые 16 KB файла (head),
		2. читаем последние 16 KB файла (tail),
		3. добавляем размер файла в байтах,
		4. считаем хеш: MD5( size + head + tail)
		5. пишем полученное значение в frontmatter sidecar-файла в поле `sidecar_hash`

3.3 Удаление (Deletion Logic)
При удалении оригинала срабатывает триггер (настраиваемый):
1. Delete Sidecar: Sidecar отправляется в корзину (Trash) вслед за оригиналом.
2. Mark as Deleted:
    - Sidecar остается.
    - В YAML добавляется тег `#sidecar/deleted`.
    - В YAML добавляется поле `sidecar_originalDeleted: ISO 8601`.
3. Ask: Диалоговое окно с вопросом пользователю.

3.4 Сканирование хранилища

Режим автосканирования (Auto-Scan):
    - Чекбокс в настройках (по умолчанию OFF).
    - Логика: Запускается после полной инициализации Obsidian и плагинов (событие `onLayoutReady`), в фоновом режиме (Live), не блокируя интерфейс.
    - Сканирует хранилище на наличие non-md файлов без пары и создает их согласно правилам.

# 4 Пользовательский Интерфейс (UX/UI)
4.1 Интерактивные Кнопки в Редакторе (Inline Buttons)
Рендеринг кнопок осуществляется так же, как это реализовано в плагине TaskNotes. Дополнительные кнопки появляются во всех режимах, не изменяя фактическое содержимое файла

Логика отображения:
1. Для текстовых ссылок (`[[file.pdf]]`):
    Рядом с ссылкой рендерятся кнопки:
    - `[Swap]`: Заменяет в коде заметки ссылку `[[file.pdf]]` <-> `[[file.pdf.md]]`.
    - `[Open]`: является ссылкой на парный файл (Sidecar или Оригинал). Поведение этой ссылки такое же, как для обычных wiki-ссылок
    - Если Sidecar отсутствует: кнопка `[Create Sidecar]`.

2. Для Embeds (`![[image.png]]`):
     Зависит от настройки "Always Show Embed Links":
     1. Enabled: Ссылка на файл отображается над картинкой (снимается скрытие класса). Кнопки `[Swap]`, `[Open]` отображаются стандартно в строке.
     2. Disabled: Ссылка скрыта. Кнопки отображаются поверх изображения (Overlay) в правом верхнем углу (внутри контейнера `.internal-embed`).

4.2 Иконка sidecar-файла
sidecar-файл необходимо визуально выделять среди других.
1. Для этого, иконка вкладки открытого sidecar-файла должна иметь не стандартную иконку md-файла, а свою собственную, как это сделано для canvas, bases, локального графа.
2. Также, в файловом проводнике таким файлам необходимо дополнительно прописывать тип расширения sidecar, как это сейчас делается для всех non-md файлов справа от их названия

4.3 Интерфейс просмотра файла (File View Overlay)
При открытии non-markdown файла (PDF, Video, Audio) в центральной области:
- Плагин внедряется в контейнер `.view-content` (используя API Electron/Obsidian для DOM-манипуляций).
- Верхняя панель: Над контентом файла отображается нативный блок Obsidian, содержащий:
     1. YAML Editor: Полноценный просмотр и редактирование Frontmatter из связанного sidecar-файла (используется стандартный компонент `MetadataEditor`).
     2. About Section: Рендеринг содержимого Markdown-секции, находящейся под заголовком `# About` (или другим, заданным в настройках) из sidecar-файла.
- В случае, когда файл-компаньон не был найден, должна высвечиваться маленькая кнопка `sidecar-file не был найден. Создать?` по нажатию на которую создается соответсвующий файл.

# 6 Команды (Command Palette)
Все команды доступны для назначения горячих клавиш:

1. Global Commands:
    - `Scan vault`: Принудительный запуск сканирования всего хранилища
	Происходит сканирование всего хранилища, проверяются все non-md файлы, подходящие под black/white lists на отсутсвие sidecar-файла. Также проверяется, что у всех sidecar-файлов существует original. если original не находится, тег `#sidecar` заменяется на тег `#Sidecar/missing`, а также добавляется поле `sidecar_originalMissingSince: ISO 8601`

2. Editor Commands (Active Note):
    - `Swap ALL links in file`: Поменять местами все ссылки в текущей заметке (Original <-> Sidecar).
    - `Convert ALL links to Sidecar`: Принудительно перевести все ссылки на Sidecar.
    - `Convert ALL links to Original`: Принудительно перевести все ссылки на Оригинал.
    - `Generate Sidecars for all links`: Создать недостающие sidecar-файлы для всех ссылок в текущей заметке.
3. Sidecar Commands (доступно только в sidecar-файле)
    - `Relink Sidecar`: Привязать активный sidecar к новому файлу (UI выбора файла).
    - `Create Sidecar for current file`: Создать пару для активного файла.

# 7 Производительность/архитектура
1. Все файловые операции выполняются асинхронно (`async/await`) с использованием воркеров (Web Workers) или очередей, чтобы избежать зависания UI (Not Blocking Main Thread). 
2. При массовых операциях отображается уведомление `Notice` с прогресс-баром.
3. в первую очередь используется api obsidian, во вторую- api electron
4. архитектура создается модульной, с возможностью дальнейшего расширения/изменения без переписывания больших участков кода

# 8 локализация 
1. интерфейс плагина должен быть не hard-code, все текстовые строки должны быть вынесены в отдельные файлы, откуда должны подгружаться в зависимости от выбранного языка, для возможности легко локализовать на нужные языке. 
2. При выборе языка Custom, плагин ищет файл `.obsidian/plugins/sidecarCreator/custom_lang.json`, откуда тянет язык. По умолчанию этот файл существует, содержит англ локализацию. Пользователь может сам создать локализацию для своего языка через этот файл

# 9 Мобильная версия
На мобильных устройствах плагин должен работать, функционал аналогичен. Никакого специального допиливания под mobile не происходит, но при этом существующую архитектуру строить так, чтоб не использовать desktop-only возможности. Адаптация под мобилки будет происходить позже, после выхода плагина в openBeta
